# Decisions

## Approach

- **Server-side filtering**: the `denials` query now takes an optional `department` argument, resolved in `server.js` by filtering the in-memory dataset. The client passes the selected department as an Apollo query variable, so Apollo automatically issues a new request (and caches each department's result) when the filter changes, instead of over-fetching all 120 rows and filtering client-side.
- **Chart dimension**: `DenialChart` aggregates by denial `reason` (sum of `amount`), not `department`. Charting by department would go degenerate once the department filter narrows the dataset to one department — every bar but one would vanish. Aggregating by reason stays meaningful in both states, and answers a more useful question when filtered ("why is Cardiology being denied?").
- **Department pie chart (`DepartmentPieChart`)**: added alongside `DenialChart`, aggregating by `department` (sum of `amount`) instead of `reason`. Bar was rejected for `reason` because 8 categories read poorly as a pie; `department` is the inverse case — only 6 fixed values (`src/types.ts` `DEPARTMENTS`), a cardinality pie charts handle well, and it's a dimension with a filter dropdown but no breakdown visualization yet. When the department filter narrows the dataset to one department, the pie correctly collapses to a single 100% slice — that's the filter working as intended, not a degenerate case to design around (unlike the reason/department-bar case above, the pie still shows real information: "yes, this is the department you filtered to").
- **Pie slice colors**: the app's existing palette (`src/index.css` `:root`) is six closely related low-chroma greys/greens, not a validated categorical or colorblind-safe palette — using only those six for six pie slices risked slices being visually indistinguishable. Rather than pick unrelated bright colors, `DepartmentPieChart` keeps two of the existing palette colors (`--dark-slate-grey`, `--iron-grey`, `--grey-olive`) and adds three new muted, low-saturation hues (a terracotta, a slate blue, an ochre/gold) chosen for lightness/hue separation while staying restrained enough to match the app's existing aesthetic rather than clashing with it. As a second, independent safeguard against relying on color perception at all, every slice also gets a direct label (department name + percentage) printed on the chart itself, so slice identity never depends on color alone — consistent with the accessibility reasoning already applied to the bar chart (see below): tooltips are not reliably screen-reader accessible, so no chart-identifying information is tooltip-only. A separate `Legend` was removed since it only repeated the same department names the direct labels already show — pure duplication, not a second safeguard.
- **Payer pie chart (`PayerPieChart`)**: added alongside `DepartmentPieChart` in the same `charts-row`, aggregating by `payer` (sum of `amount`) instead of `department`. Pie was chosen for the same reason as the department chart: the mock dataset has exactly 5 fixed payer values, a cardinality pies handle well, and there was no existing breakdown-by-payer visualization (the dedicated "Payer Breakdown" tab is a separate, still-unimplemented "Coming soon" feature — this card answers a narrower "which payers denied the most dollars" question inline on the Breakdown view). It reuses `DepartmentPieChart`'s exact structure (on-slice `payer: XX%` labels, no `Legend` — same anti-duplication reasoning as that chart — `chart-card-exhibit`/`chart-card-title`/`chart-card-body`/`chart-card-caption`, empty state, `currency()` tooltip formatter) so the two pie cards are visually and behaviorally consistent. Colors are five new muted, low-saturation hues (plum, bronze/khaki, teal, plus reuses of `--dark-slate-grey`/`--iron-grey`) chosen to be distinguishable from each other and, as much as reasonably possible, from `DepartmentPieChart`'s palette, so the two cards sitting side by side don't visually alias.
- **Hardcoded department list**: the filter's option list comes from a small constant (`src/types.ts`), not from the query results, so the dropdown doesn't shrink to whatever department happens to be selected.
- **Component library (Radix UI + TanStack Table)**: per the survey in `research/component-libraries/`, the department filter uses `@radix-ui/react-select` and the denials table uses `@tanstack/react-table` for sorting — both headless/unstyled, so the existing custom visual identity (palette, Rajdhani font, layered sidebar) didn't need to be rebuilt around someone else's design system. The cost is that all visual styling for these controls (`index.css`) had to be written by hand rather than coming for free.
- **Per-card chart-type switcher**: each chart card (`DenialChart`, `DepartmentPieChart`, `TrendSparkline`) got a small dropdown in its header (`ChartTypeSelect`, next to `.chart-card-title`) letting the user change how that card's own aggregated data is drawn. Reused `@radix-ui/react-select` (already a dependency, used by `LabeledSelect`) rather than pulling in `@radix-ui/react-dropdown-menu` — this is a value-select (one of N mutually exclusive views), not an action menu, so the existing Select primitive is the right fit, just re-styled as a compact icon-trigger (`.chart-type-select-*` in `index.css`) instead of `LabeledSelect`'s block-style filter-bar look.
- **Which chart types per card, and why they differ**: `DenialChart` (by `reason`, 8 categories) and `DepartmentPieChart` (by `department`, 6 categories) both aggregate to the same "category → total" shape, so they share one option set (`CATEGORICAL_CHART_TYPES` in `src/chartTypes.ts`): bar, pie, and a plain sorted table (a third option, not just bar/pie, per the brief) — all three render the identical aggregated array with no reshaping. `TrendSparkline` aggregates by month instead — ordered points along a continuous axis, not independent categories — so it gets its own option set (`TIME_SERIES_CHART_TYPES`): area (the original default), line, and bar-by-month. A pie option is deliberately *not* offered on the trend card: "how did this change over time" isn't a question a pie chart can answer, and forcing one in for consistency with the other two cards would just produce a nonsensical chart, not a real choice. Each card still defaults to its original chart type (bar for Reasons, pie for Departments, area for Trend) so existing behavior doesn't change until the user opts into something else.
- **Persistence**: each card's chosen chart type is written to `localStorage` under `denial-dashboard:chart-type:<key>` (`reason` / `department` / `trend`), via `useChartType()` in `src/chartTypes.ts` — the same `useState` + `loadStored*()`-fallback-to-default + try/catch-write-through pattern already used for font/palette/radius/nav-mode in `useThemePreferences.ts`, rather than a new mechanism. The choice survives a reload the same way every other display preference in this app already does.
- **Generalized into `CategoryCard`/`TimeSeriesCard`**: with a third near-identical card (`PayerPieChart`) added alongside `DenialChart`/`DepartmentPieChart`, the three were no longer just superficially similar — they were the exact same component (aggregation → `BarView`/`PieView`/`TableView` → chart-type switcher → skeleton/empty states) differing only in which `Denial` field to group by, an optional per-category color map, the default chart type, and title/caption text. `CategoryCard` (`src/components/CategoryCard.tsx`) now takes that as a `CategoryCardConfig` object; `DenialChart`/`DepartmentPieChart`/`PayerPieChart` were deleted and replaced by three config constants in `BreakdownPage.tsx` (`REASON_CARD`/`DEPARTMENT_CARD`/`PAYER_CARD`). `TrendSparkline` became `TimeSeriesCard` + `TREND_CARD` the same way, even though only one time-series card exists today, so a second one (e.g. a future denial-count-over-time card) doesn't have to re-copy the shell. One behavior change fell out of generalizing `BarView`: reason bars, which previously rendered as one flat color, now get a `Cell` per category from a shared positional palette (`DEFAULT_SLICE_COLORS`) when a card has no explicit `colors` map — consistent with how every pie view already colors its slices, rather than bar and pie disagreeing on whether categories get distinct colors.
- **Accessibility carried over to every view**: the `TableView` variants use a real `<table>` with `<caption>`/`scope="col"` headers, so switching a categorical card to "Table" doesn't lose anything a screen reader could already get from `DenialsTable` — it's just another accessible rendering of the same data, not a new gap. `DepartmentPieChart` keeps its direct on-slice labels (and still no `Legend`) regardless of chart type. Each card's `<section aria-label>` and `<h2>` title are untouched; the new `Select.Trigger` gets its own descriptive `aria-label` (worded to avoid substring-colliding with the existing `/department/i` / `/period/i` filter-bar test queries, e.g. "Dept. breakdown chart type" instead of literally "Chart type for Departments").
- **Static per-tab routes instead of a dynamic `/:tabId` segment**: `App.tsx` registers one explicit `<Route path="/breakdown">`, `<Route path="/settings">`, etc. (one per `TABS` entry) rather than a single `<Route path="/:tabId">` matching any string, plus a top-level `<Route path="*">` redirecting anything unmatched to the default tab. Each route renders its own dedicated page component (`BreakdownPage`, `SettingsPage`, or the shared `ComingSoon` placeholder — see `tabPages.ts`) instead of one component branching on `activeTab` internally. A shared `DashboardLayout` (a pathless layout route rendering `<Outlet>`) owns the chrome common to every tab — filter bar, command palette, sidebar/topbar shell, theme/nav-mode state — and passes what child pages need down via `useOutletContext`.
- **Period filter is client-side, anchored to the data's own latest date**: `src/periods.ts` filters the already-fetched denials by date range in the browser rather than adding a second GraphQL argument, since the "current date" concept only needs to be relative to what's in the dataset. "Today" for period math (`this month`, `this quarter`, etc.) is the most recent denial's date, not the real calendar date — the mock dataset ends mid-2025, so anchoring to the real system clock would make every period option resolve to zero results.
- **Payer filter, server-side like department**: added a `payer` GraphQL argument alongside `department` (`server.js` filters on both independently -- either, both, or neither can be set), a `PayerSelect` dropdown next to `DepartmentSelect` in the filter bar, and matching `Filter by Payer` command-palette entries. Server-side rather than client-side for the same reason as department: payload size scales with the filtered result, not the full 120-row dataset. Reused `PAYER_CARD`'s existing colors/aggregation for the visualization rather than adding a new chart, since the payer breakdown card already existed (added alongside the department filter earlier) -- the filter was the missing half, not the chart. Had to reword `PAYER_CARD`'s chart-type-select `aria-label` from "Chart type for Payers" to "Insurer breakdown chart type" once a real `/payer/i`-matching filter combobox existed, for the same substring-collision reason `DEPARTMENT_CARD` already avoids "Chart type for Departments".
- **Reason filter, server-side like department/payer**: same pattern again -- a `reason` GraphQL argument (all three of `department`/`payer`/`reason` filter independently in `server.js`), a `ReasonSelect` dropdown, and `Filter by Reason` command-palette entries. `REASON_CARD`'s chart-type-select `aria-label` needed the same "Chart type for Reasons" → "Denial breakdown chart type" rewording as the department/payer cards did, to avoid colliding with the new `/reason/i`-matching filter combobox in tests.
- **Grid layout for the charts row (superseded, see below)**: `.charts-row` switched from `flex-wrap` to `display: grid; grid-template-columns: repeat(3, 1fr)`, with the trend card given `grid-column: 1 / -1` to span the full width of its own row beneath the three category cards. Grid was chosen over flex specifically because the trend card's "span the whole row" requirement needs real columns to lock onto -- flex-wrap can't express "this item takes 100% while its siblings share three equal columns" without fragile width math.
- **Back to `flex-wrap` once the pie cards had a real min-width to wrap around**: once `CategoryCard`'s pie view was given an actual `minWidth` (the pie's assumed diameter plus its widest label on each side -- see `PieView`'s `minWidth` prop), that same min-width doubles as the natural wrap threshold for the whole row, making the earlier objection to flex-wrap moot -- a flex item's own min-content width (now non-trivial for a pie card) is exactly what `flex: 1 1 360px` needs to decide when 3 cards no longer fit and one should drop to the next line. This replaces the previous grid + fixed `max-width: 1000px` media query breakpoint with continuous reflow: cards grow/shrink to share whatever width is available and only wrap once they'd be squeezed narrower than a pie chart can stay legible, rather than jumping between two hardcoded states. The trend card still always takes its own full-width row -- expressed as `flex: 1 1 100%` (a flex-wrap item at 100% basis always starts a new line) rather than grid's `grid-column: 1 / -1`, since flex-wrap can express "this item takes the whole row" just as directly once it isn't also being asked to lock three siblings to strictly equal columns.
- **Removed `.dashboard`'s `min-width: fit-content`**: a long-standing rule from early in the project, from before the charts row had any meaningful min-width of its own. Once the pie cards gained a real `minWidth` and `.charts-row` switched to flex-wrap, `fit-content` on this ancestor started actively fighting the wrap it was supposed to enable -- `fit-content` sizes an element to its content's *unwrapped* minimum, so the page itself could never get narrower than "3 cards side by side," producing a horizontal scrollbar even once the row had wrapped down to fewer cards per line and nothing was visibly overflowing. The sidebar layout doesn't actually depend on this rule: `.sidebar` already has a fixed, non-shrinking `flex: 0 0 220px`, and `.dashboard-layout .dashboard-content` already opts into shrinking via its own `min-width: 0` -- so removing it lets the page (and the chart row inside it) shrink down to the viewport width as intended.
- **Zero-layout-shift loading state**: the initial query's `loading` state used to render a bare `<p>Loading...</p>` in place of the whole dashboard, so every chart, the summary panel, and the table popped into existence at once the moment data arrived — a jarring shift, worse the longer the request takes. Now `Dashboard` always renders the full tab content and passes a `loading` flag down to each chart/table, so the same DOM structure at the same dimensions is present throughout: each chart card renders a `.chart-skeleton` placeholder sized to fill the exact box the real `ResponsiveContainer` chart will occupy, and `DenialsTable` renders 8 skeleton rows via `.skeleton-text` spans instead of the single "No denials found." row. The one part of the page that can't fully avoid a size change is the records table's *row count* — final row count (anywhere from 0 to 120+) isn't knowable before data arrives, so `.denial-records-table-scroll` gives that table a fixed `max-height` with internal scroll (sticky header) instead, keeping the outer page layout stable even though the table's own scrollable content still grows.
- **`TimeSeriesCard` and `CategoryCard` both omit themselves for single-item data, on purpose**: `TimeSeriesCard` returns `null` whenever a non-loading trend has ≤1 month of data (a single point has no trend/shape to show), and `CategoryCard` returns `null` whenever it has ≤1 category (a single bar/slice/row has nothing to compare against) — both checked after the loading state, so the loading skeleton still shows normally while a query is in flight, and both cards can still legitimately appear/disappear as filters change without that reading as a bug, since the card cleanly vanishes rather than rendering a single meaningless data point. This briefly regressed to "always render, even for 1 data point" while chasing an unrelated CSS bug that made the trend card's chart area blank (a `flex-basis` conflict, not this guard — see below) — restored once that render bug was actually found and fixed. This is a deliberate reversal of the reasoning documented below for the Trends page's multi-series chart (a single flat line there is still informative, "here's this one filtered category's trend") — `CategoryCard`/`TimeSeriesCard` favor omitting a single-item chart entirely instead.

- **Visual polish pass**: deepened card/content-pane shadows slightly (`0 1px 4px` → `0 2px 8px`, same opacity) so cards read as more crisply separated from the page rather than nearly flush with it. Gave `.chart-card-title` explicit `1.15rem`/`700` sizing so it clearly outranks the chart-type dropdown and caption sitting next to/below it, rather than inheriting an unstyled `h2`.
- **Denial-Level Detail table header matches the summary panel**: the bare `th` rule (used by `DenialsTable`, distinct from `.chart-card-table th` used inside chart cards) now uses `background-color: var(--dark-slate-grey)` with `color: var(--silver)` — the exact same fill/label-color pairing `.summary-panel`/`.summary-card-label` already use, so the records table's header reads as the same dark-surface treatment as the summary stats directly above it rather than a separately-styled surface. (An earlier pass had instead made this `th` match `.chart-card-table`'s light/transparent treatment for a different reason — consistency with the chart cards' tables — but the summary-panel pairing was chosen as the better match once asked to compare directly against it.) Since `th` is opaque again, the sticky-header rule (`.denial-records-table-scroll thead th`) no longer needs its own background override to mask rows scrolling underneath it.
- **Pie label wrapping made deterministic**: `CategoryCard`'s `PieView` passed a plain string (`` `${category}: ${pct}%` ``) as `Pie`'s `label` prop, leaving Recharts/the browser's own text layout to decide where each label wrapped — different slices broke at different, seemingly arbitrary points depending on name length and slice angle (e.g. "Radiology:\n46%" vs. "Orthopedics: 54%" on the same chart). Replaced it with a label-rendering function that returns an explicit two-`<tspan>` `<text>` element (category name, then percentage, at fixed `dy` offsets) — Recharts renders a function's returned React element directly rather than wrapping it, so every slice now wraps identically regardless of name length. Reduced `outerRadius` from `55%` to `50%` at the same time to give the now-two-line labels a bit more radial room.
- **Payer bar chart's Y-axis width**: bumped the non-`wide` `YAxis` width from `100` to `120` — "Medicare" (the longest payer name) was rendering flush against the plot area with no margin at the old width.

## Performance

- Filtering server-side means payload size and render work scale with the filtered result set, not the full dataset — matters more as denial volume grows well past 120 rows.
- Chart aggregation (grouping by `reason`) is wrapped in `useMemo`, keyed on `data`, so it isn't recomputed on unrelated re-renders.
- `useQuery`'s `previousData` is rendered alongside `data` while a filter change is in flight, so switching departments doesn't blank the table/chart back to a loading state on every selection — avoids a jarring flash/layout jump, at the cost of a brief moment showing stale data during refetch (acceptable trade for a filter that resolves in milliseconds against the mock server).
- `ResponsiveContainer` (Recharts) handles resize without manual window-resize listeners or fixed pixel dimensions.

## Accessibility

- Both filters (Radix `Select`s, via the shared `LabeledSelect`) have a properly associated, visible `<label htmlFor>` plus an explicit `aria-label`, and Radix handles the underlying keyboard navigation/focus management/ARIA roles for the listbox itself.
- Each chart is wrapped in its own `<section aria-label="...">` with a real, visible `<h2>` heading (not just a styled div), so its purpose is announced to assistive tech, not just implied visually. `DepartmentPieChart` mirrors this pattern from `DenialChart`.
- Recharts renders plain SVG with limited built-in ARIA semantics in this version (2.6.2) — in particular, tooltips are mouse/focus-triggered and not reliably read by screen readers. The existing denials table is left in place alongside the charts and exposes the same underlying data in a natively accessible, keyboard-navigable form, so no information is chart-only. `DepartmentPieChart` additionally never relies on its tooltip for slice identity — direct on-slice labels cover that instead (see above).
- The error state uses `role="alert"` for assertive announcement of query failures.

- **Standalone "Trends" page**: the nav tab labeled "Trends Over Time" previously routed to a `ComingSoon` placeholder — the only real time-series chart lived embedded inside `BreakdownPage`'s `charts-row` (`TimeSeriesCard`/`TREND_CARD`), which stays there unchanged as a quick single-line glance. The new `/trends` page (`TrendsPage`) is a deeper, separate view: the user picks one dimension (Department/Reason/Payer) and every value in it becomes its own line on a shared monthly/weekly timeline (`useMultiSeriesTrend`), aggregating by sum of `amount` the same way every other chart in the app does. Tab label shortened to just "Trends" at the same time, since the page itself now explains what it is.
- **Multi-line series identity, not free-form series picking**: the line-dimension picker offers exactly one of Department/Reason/Payer at a time (switching swaps the whole line set) rather than letting the user freely mix individual values across dimensions — keeps every line on the chart answering the same comparable question ("which departments are trending worst") instead of producing incoherent pairings (a department line next to a payer line).
- **Series list comes from the fixed canonical constants** (`DEPARTMENTS`/`PAYERS`/`REASONS` in `types.ts`), not from what happens to appear in a given bucket — same reasoning as the existing filter-dropdown constants: keeps line count/order/color stable as filters and time buckets change, rather than lines appearing/disappearing.
- **Degenerate single-line case is allowed, not designed around**: picking "Department" as the line-dimension while the Department *filter* is also narrowed to one department produces a single flat line. Consistent with `DepartmentPieChart`'s existing precedent (a filtered pie collapsing to one slice is the filter working as intended), no exclusion/warning UI was added for this case.
- **Color reuse across pages**: Department/Payer lines on the Trends page reuse the exact same `DEPARTMENT_COLORS`/`PAYER_COLORS` maps as the Breakdown page's pie/bar cards (now exported from `BreakdownPage.tsx`), so a given department/payer is the same color on both pages. Reason (which has no fixed map) falls back to `CategoryCard`'s `DEFAULT_SLICE_COLORS` positional palette (now exported), indexed by fixed array position rather than first-appearance order, for the same color-stability reason as the series list above.
- **Weekly bucketing, hand-rolled ISO-8601 weeks**: no date library exists in this project (`periods.ts` already hand-rolls month/quarter math with plain `Date`s), so `trendBuckets.ts`'s `bucketByWeek` follows the same convention — standard dependency-free ISO week algorithm (shift to the week's Thursday, count weeks from the year's first Thursday). Week labels are short (`"Wk 7"`) rather than calendar ranges (`"Mar 12–18"`), since a full range would overflow the x-axis once ~13-53 weekly buckets are on screen at once — a trade-off worth revisiting (e.g. moving the full range into the tooltip) if weekly granularity turns out to be heavily used.
- **Period-over-period (PoP) disabled for "All Time"**: "All Time" has no bounded window, so there's no non-arbitrary definition of "the previous period" to compare against (a prior 12 months? the first half of the dataset?) — any such window would be an invented comparison, not a period-over-period view of the filter the user actually chose. The PoP toggle stays visible but `disabled` (with an explanatory `title`) rather than being hidden, consistent with this app's controls never conditionally unmounting.
- **PoP's "previous period" is the immediately preceding window of the same length** (e.g. "this quarter" → the 3 calendar months directly before it), not "the same window one year back" — one of a few reasonable interpretations, called out explicitly since it directly shapes what the comparison means. `last-30`'s previous period is the preceding 30-day window (days 31–60 back).
- **PoP overlay aligns by relative position, not calendar date**: both periods are re-bucketed independently, then indexed by ordinal position within their own period ("Month 1", "Month 2"...) rather than absolute month/week key — this is what lets "month 1 of this quarter" line up against "month 1 of last quarter" regardless of which actual calendar months they fall on. Each series renders twice — solid (current) and dashed at the same color (previous) — so current-vs-previous is distinguished by stroke style rather than doubling the color palette, preserving the "same category = same color" mental model from the rest of the app. This does mean the Reason dimension's PoP view can show up to 16 lines at once (8 reasons × 2); accepted as the cost of showing the overlay and the delta strip together, per explicit product direction, rather than a smaller/staged view.
- **Delta-stat strip shows a fixed 4 items, not one stat per line**: a headline total (current vs. previous, with % change) plus the top 3 movers by *absolute dollar* change — not percent change, since percent change on a small base can be misleadingly large (e.g. $50→$150 reads as "+200%" but is immaterial) while dollar magnitude matches how every other aggregate in this app (`SummaryStats`, `CategoryCard`, `TimeSeriesCard`) already ranks by sum of `amount`. Capped at 3 regardless of dimension so the strip stays a fixed, scannable size even for Reason's 8 series.
- **Moving average smooths the line in place, not as a second overlay line (Trends page)**: a per-series trailing simple moving average (`trendMovingAverage.ts`), selectable as Off / 3-period / 6-period ("period" tracks whichever granularity — month or week — is active), replaces each series' own plotted value with its smoothed value rather than adding a second dashed "average" line alongside the raw one. First tried as a separate overlay line, but the raw and averaged lines competing for attention on the same chart was worse than just showing the smoothed trend directly — since the point of a moving average is to see the trend more clearly, not to compare it against the noisy original. The first `window - 1` buckets of each series keep their raw value rather than being averaged over a shorter partial window, which would understate the real smoothing and put a visible kink in the line right where the full window kicks in. The control is disabled (with an explanatory `title`) whenever period-over-period comparison is on, since PoP's overlay already carries its own meaning (solid = current, dashed = previous) that smoothing would complicate.

- **Metric filter (dollar amount vs. denial count), applied app-wide**: a new `Metric` filter-bar control (`MetricSelect`, backed by `filters.metric`/`filters.setMetric` in `useDashboardFilters`, URL-persisted like every other filter) switches every chart's aggregation between "sum of `amount`" and "count of denials" via a single shared helper, `metricValue(denial, metric)` in `types.ts` (returns `denial.amount`, or `1` so summing yields a count). Threaded through every aggregation site that used to hardcode `d.amount`: `CategoryCard`'s `useCategoryTotals`, `TimeSeriesCard`'s `useMonthlyTrend`, `useMultiSeriesTrend`, `trendPeriods.ts`'s PoP bucketing, and `SummaryStats`. Chosen as one global filter rather than a per-chart toggle so the whole dashboard tells a consistent story ("what am I looking at right now") instead of some cards showing dollars and others showing counts with no visual cue why.
- **"Average Denial" stays a dollar figure regardless of the metric filter**: switching the metric to "Denial Count" would make a naive per-metric average trivially `1` (each denial contributes exactly 1 to its own count, so `total/count` always equals 1) — a stat that's always 1 conveys nothing. `SummaryStats` keeps this one card computing the average dollar amount per denial unconditionally, while "Total Denied"/"Total Denials" (the headline stat) and the "Top Reason" ranking do switch with the metric filter, since those remain meaningful in both modes.
- **Currency formatting swaps for plain-number formatting when the metric is "count"**, not just relabeling: every chart's axis ticks, tooltips, table cells, and delta-stat strip use a metric-aware formatter (`formatterFor`/`compactFormatterFor` in each chart file) rather than always prefixing `$` — a "$2" total denial count would be actively misleading, not just stylistically off.

- **Fixed bar thickness (`27px` floor, `40px` target), and card height driven by content instead of a fixed 576px**: the bar-view's `<Bar>` used to fill whatever height the card's fixed `576px` gave it, divided evenly across categories — fine for Reasons' 8 categories, but Payers (5) or Departments (6) ended up with unreasonably thick bars. `CategoryCard.tsx` now renders each bar at a fixed `barSize` (`BAR_THICKNESS`, derived as `Math.max(MIN_BAR_THICKNESS, MAX_BAR_THICKNESS)` so the floor is enforced in code, not just by convention) rather than Recharts' `maxBarSize` (which only caps thickness, it doesn't guarantee bars actually render at that size) — `barSize` renders every bar at exactly that thickness regardless of category count. `barChartHeight(categoryCount)` derives the chart's own height from that same fixed thickness instead of stretching to fill an ambient fixed height, so a card with fewer categories is simply a shorter card. `.charts-row > section` no longer sets `height: 576px` at all.
- **`PieView`'s height was pinned to its *minimum* width, not its actual rendered width**: a follow-up fix to the entry above — giving the pie an explicit `height={minWidth}` used the `minWidth` *floor* value (the pie's assumed diameter plus its widest label) as a fixed height regardless of how wide the card actually rendered, so a pie in a wide card (many category cards now stretch well past that floor once flex-wrap gives them extra row space) still had its height pinned to the narrow-case minimum — either leaving dead vertical space if the pie itself grew wider without growing taller, or breaking its circular aspect ratio, depending on how the mismatch resolved. An interim fix used `aspect={1}` + `maxHeight` (height tracks the pie's actual rendered width, capped at the same value used for the width floor, so the pie grows with the card up to its natural minimum-comfortable size and stops) — see the next entry for why that width-derived height was itself still too generous.
- **Pie container height no longer scales with the label's width margin**: `aspect={1}` kept the pie *square*, so its height still inherited the *width* formula (`ASSUMED_PIE_DIAMETER + widestLabelWidth(chartData) * 2`) — sized for the *widest category name* sticking out to either side. But the label's vertical footprint is always exactly 2 fixed lines (`renderPieLabel`'s two `<tspan>`s: category name, then percentage), regardless of how long that category name is — so reserving width-sized vertical margin was excess space above/below the circle that the label never actually used.
